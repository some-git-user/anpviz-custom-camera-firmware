[custom14] 2026-10-10  -- Nagios feed moved to an unguessable path
  - PROBLEM: the telemetry feed was served at the guessable static path
    /nagios.txt with NO authentication -- anyone on the LAN could read it.
  - YM500L cannot get the YMF46D-style authenticated /cgi-bin/nagios route:
    its web_server is a stripped gSOAP binary with no CGI dispatcher, and the
    static-file handler opens files via RAW SYSCALLS (verified with the
    cve_log observer: /nagios.txt never appears in the libc open log). There
    is no LD_PRELOAD interposition point that sees the request URI. Adding
    real per-request auth would require binary-patching the vendor web_server.
  - FIX (zero-RE): serve the feed ONLY at /nagios_<token>.txt and delete the
    guessable nagios.txt. The token is a stable per-camera secret (same store
    pattern as the recovery password: tools/.nagios_token.<ip>, gitignored).
    pack.sh generates the tokenised symlink every pack; the open nagios.txt is
    removed from the tree. The Nagios poller passes --path /nagios_<token>.txt.
  - This is a capability URL (shared secret), not login auth -- but it closes
    the unauthenticated-read hole. See repo memory ym500l-nagios-auth-re.md.
  - Also: telnet recovery-login attempts are now counted. reclogin.sh appends
    one epoch second per attempt (success OR failure) to /tmp/telnet_attempts.log;
    nagios.sh feed schema 4 turns it into telnet_attempts_5m. This path bypasses
    web_server entirely, so login_watch.so cannot see it -- the counter lives in
    the script. Checker: --warn-telnet (default 1) / --crit-telnet (default 3);
    telnet is off by default so any attempt is notable. Detection only.

[custom5] 2026-10-04  -- Hardware Diagnostics UI panel ported

    Version Info page. Two files touched:
      var/www/html/versionConfig.html  + the hwinfo_section div block
      var/www/js/versionConfig.js      + the "Hardware Diagnostics" IIFE,
                                       copied BYTE-IDENTICAL from YMF46D
    Cost: ~2.3 KB compressed. rootfs 9,056,256 = 57,344 under the stock limit.
  - The IIFE is deliberately non-invasive: it monkey-patches
    Page.versionConfig.render inside try/catch and wires #hwinfo_refresh, so a
    failure degrades to an error box in the panel and never breaks the page.
  - Field coverage verified against the LIVE YM500L feed: 38/38 fields present,
    0 unpopulated. No field mapping needed -- hwinfo.sh is the same portable
    script on both cameras and resolves platform differences at runtime
    (machine=INFINITY3 MSC000A-S04A, soc_family=I3, kernel=3.18.30,
    temperature via cpufreq/temp_out).
  - Port recipe, for the next camera: YMF46D's versionConfig.js line 1 is stock,
    so lines 2..end are purely our addition. Append those bytes to the target's
    single-line file. Verified byte-identical after.

  FEED AUTH GATING -- INVESTIGATED, NOT POSSIBLE ON THIS MODEL.
    The static feeds (/hwinfo.txt, /nagios.txt) are world-readable on the LAN
    and cannot be gated by the vendor web_server:
      * http_cgi_find / http_cgi_handle / cgi_get_value are ABSENT. On YMF46D
        those live in libcgibin_curl.so, not in web_server -- the shim there
        interposes on the lib. That library DOES NOT EXIST on this model.
      * web_server exports 487 FUNCs but ZERO request-path/CGI/auth hooks.
        MsgUserGetPassword IS exported, but with no dispatch hook it is useless
        on its own.
      * Every Authorization / WWW-Authenticate string in web_server belongs to
        ONVIF / RTSP / TLS, not static-file auth.
      * No iptables on the device. No busybox httpd applet.
      * Empirically: /, /index.html, /hwinfo.txt, /nagios.txt and
        /CUSTOM_BUILD.txt all return 200 with no www-authenticate header.
        Missing files ALSO return 200 (the Welcome-page masquerade), so the
        status code proves nothing on this server.
    Remaining options if we ever want this gated: run our own authenticated
    server on a free port, or enforce it at the router. Both are real work.
    NOTE the same exposure already exists on YMF46D for hwinfo.txt -- only the
    nagios feed has the shim there.

  SIZE GATE — RESOLVED (this build settles it).
    The vendor updater's check lives in mainctrl:
      "filesys file size %d too small."
      "filesys file size %d too large."
      "filesys file size %d too large, max value: %d."
    An image at stock + 4096 (9,117,696) is REJECTED by the updater. An
    image at 9,109,504 = 139 x 64 KiB -- 4,096 UNDER stock (9,113,600)
    but 65,536 above the previously installed image -- is ACCEPTED.
    Therefore:
      * the gate is NOT "<= currently installed size"  (disproved here)
      * erase-block alignment is NOT required (stock itself is unaligned)
      * the limit is derived from stock / the image header, not the 11 MiB
        mtd2 partition (which would allow far more)
    Practical rule for future YM500L builds: keep rootfs_size <= 9,113,600.
    pack.sh gained ROOTFS_PAD_MULT (or build.info rootfs_pad_multiple=) to
    round the rootfs to an erase-block multiple; harmless, but not required.

  CAVEAT -- TEMPERATURE BASELINE IS HIGH ON THIS MODEL.
    The sensor tracks real thermal state with a slow time constant: a stable
    ~88-89 C at rest, against 93-96 C when warm. Let the box settle before
    trusting a reading -- a measurement taken right after load looks pinned.
    What keeps it hot: the vendor media pipeline never idles. media_server holds
    ~45% CPU and ~0.0% idle was observed even with no client connected, so the
    SoC sits near the top of its normal band permanently. YMF46D reads ~74 C
    at comparable load (~15 C lower, different SoC).
    Because nagios.sh is shared and ships ONE default threshold pair
    (warn 75 / crit 85), YM500L reports CRITICAL at its NORMAL RESTING state.
    FIX IN NAGIOS, NOT IN THE SCRIPT: set --warn-temp 92 --crit-temp 97 for
    this host. Do not raise the script default -- that would blind YMF46D.
    LESSON: let these boxes settle before trusting a thermal measurement.

  NOTE -- nand is small: /dev/block/mtdblock4 jffs2, 512 KB total
    (236 used / 276 free = 46%). nand_used_pct on this camera is a real,
    tight metric worth alerting on.
